# BLOCKING CONSTRAINTS — Read Before Anything Else

> These are not suggestions. Each was discovered through actual failure this session.
> Acknowledge each one explicitly before proceeding.

- [ ] CONSTRAINT: **`root-gpu` in h3's profile is a floor, not a total** — `h3_gpu.h` documents that `gpu_seconds` counts only root `MTLCommandBuffer` timestamps and that MPSGraph schedules child buffers it never times. The denoise issues 1000 MPSGraph dispatches. Reading `root-gpu` as total GPU time produced a false "59% of the run is idle waiting" conclusion that was fed to three peer reviewers and shaped their top recommendations. — Mitigation: use `command_wait_seconds` as the complete turnaround measurement, and never quote `root-gpu` as a total.

- [ ] CONSTRAINT: **Verify output bit-identity after every perf change** — an item-2 bug (weight loader `pread`ing into staging without blitting it across) produced a **flat grey frame** while exiting 0 and writing a valid 22-frame h264+AAC MP4. `ffprobe` passed. Only looking at pixels caught it. — Mitigation: `cmp <new>.mp4 outputs/h3-egpu-test.mp4` after every change; the reference md5 is `886b40d10c5a83fb01393a4c62bdfcbd`. Extract a frame grid and *look at it* when the file changes.

- [ ] CONSTRAINT: **Do not project a win from one bottleneck reading** — optimization A was projected at 139 s → ~100 s from the read/DMA split. It delivered −31% DMA wait and −23% stream time and **zero** end-to-end change. The projection method was wrong, not the measurement. — Mitigation: attribute the *whole* phase wall before predicting; if the terms do not sum to the wall, there is an unidentified serialization and any projection is guesswork.

**Do not proceed until all boxes are checked.**

<context>
This workload is **bus-bound, not compute-bound**, and that single fact should
drive every remaining decision. Confirmed numbers: host→VRAM DMA runs at
1.68 GB/s, which is 96% of what the 20 Gb/s Thunderbolt link sustains. GPU

bytes*; making kernels faster is worthless.

The two big wins came from realising h3.c is written for unified memory: it put
every buffer in `MTLResourceStorageModeShared`, which on an eGPU means host
memory across a cable at 1.76 GB/s versus 478 GB/s in VRAM — a 270× gap. That,
plus its 16×16 tile kernel re-reading each weight once per 16 output rows, made a
single dispatch take 23 s and trip the macOS GPU watchdog.

invariant: if a change alters the md5, it is wrong until proven otherwise.

# revontuli

**Local MiniMax H3 video generation on an Intel Mac with an AMD eGPU.**

*Revontuli* — Finnish for the aurora, from *revontulet*, "fox-fires": the myth that an
arctic fox racing across the snow sweeps sparks into the sky with its tail. This
project's benchmark clip is a red fox walking through snow, generated by a Radeon
glowing over Thunderbolt on a machine none of this stack was designed for.

This repository is the working port, the performance investigation that took a
generation from **51.4 minutes to 4.0 minutes** (12.7×, bit-identical output), and the
diagnosis + fix for a **silent data-corruption bug in Apple's MPSGraph
`scaledDotProductAttention`** that anyone running long attention sequences through
MPSGraph should know about — on any GPU, not just AMD.

| clip | frames | duration | wall time |
|---|---|---|---|
| `outputs/h3-egpu-test.mp4` | 22 | 0.92 s | 4.0 min |
| `outputs/fox-73f.mp4` | 73 | 3.04 s | 9.3 min |
| `outputs/fox-5sec-fixed.mp4` | 124 | 5.17 s | 14.2 min |

608×352, 4 denoising steps, synchronized AAC audio, on a 2018 Mac mini (i7-8700B) with
a Radeon RX 6900 XT in a Thunderbolt 3 enclosure.

## The MPSGraph SDPA bug (read this even if you don't care about foxes)

MPSGraph's native `scaledDotProductAttentionWithQueryTensor:` **silently corrupts
attention when its internal scores tensor `[heads, seq, seq]` crosses 2³¹ elements.**

- Measured to the single integer on gfx1030: with 56 heads, **seq 6192 is correct,
  seq 6193 is broken** (56·6193² is the first product past 2³¹).
- Broken heads return **near-uniform attention** — no error, no NaN, all values in
  range. Your model doesn't crash; it quietly produces low-contrast mush.
- The broken head set grows **from both ends of the head range** as seq rises
  (int32 wraparound): `{0}` at 6193 → `{0,1,55}` at 6250 → `{0..8, 48..55}` at 6700.
- Head-major and row-major layouts fail identically. Random-data testing will NOT
  catch it (uniform attention on random data looks almost correct — err ~0.007);
  it takes a planted high-logit spike to expose err ~1.0.
- The same oversized tensor also drives MPSGraph's CPU-side planner pathological:
  per-dispatch encode went 0.25 s → 1582.7 s at seq ~7995.

**Standalone reproducer:** `src/sdpa_probe.m` (~330 lines, no model needed). It builds
the exact production graph, plants one spike per head, and maps which (head, query)
cells break at any sequence length. `--split` enables the fix for A/B.

**The fix** (patch 0012, `h3_gpu.m`): when `heads·seq² > 1.9e9`, slice the head
dimension inside the graph, run SDPA per chunk, concat. Below the gate the graph is
byte-identical to the unsplit one — the 22-frame reference md5 is unchanged. The gate
is size-based, not vendor-based; Apple Silicon at long sequences may need it too.

Full investigation trail: `logs/51-INVESTIGATION-STATE.md`, measurements in
`logs/5[2-5]-sdpa-*.log`.

## What you need

- **A Metal-visible discrete GPU with ≥16 GiB VRAM.** Developed and verified on a
  Radeon RX 6900 XT (`amdgpu_gfx1030`) in a Thunderbolt 3 enclosure. eGPU support
  requires an **Intel** Mac (Apple Silicon Macs do not support eGPUs).
- macOS 15.x (built on 15.7.9), Xcode or Command Line Tools (clang with ObjC ARC).
- **~140 GiB disk** for the model snapshot, plus a few GiB working space.
- 64 GiB RAM recommended (the streamed-weights path reads 144 GiB per generation
  through the page cache; it works with less RAM, just slower on repeat runs).
- `ffmpeg` (`brew install ffmpeg`) and Python 3 for the model download.

## Setup

```bash
git clone https://github.com/mindless/revontuli && cd revontuli

# 1. Get the patched h3.c fork
git clone -b intel-amd-egpu https://github.com/mindless/h3.c.git src/h3.c
cd src/h3.c
make -j"$(sysctl -n hw.logicalcpu)"
H3_METAL_DEVICE_NAME="6900" make test        # ok: 1769 checks
cd ../..

# 2. Confirm macOS exposes your eGPU to Metal (must print your card)
xcrun clang -fobjc-arc -framework Foundation -framework Metal \
  src/metal_probe.m -o bin/metal_probe && ./bin/metal_probe

# 3. Prove the operations h3.c needs work on that GPU (11 checks)
xcrun clang -fobjc-arc -O2 -framework Foundation -framework Metal \
  -framework MetalPerformanceShaders -framework MetalPerformanceShadersGraph \
  src/h3_capability.m -o bin/h3_capability
./bin/h3_capability 6900 src/h3.c/h3_shaders.metal

# 4. Download the FL2VA weights (134 GiB; resumes on failure)
python3 -m venv venv && venv/bin/pip install -q huggingface_hub[cli]
./bin/download_model.sh

# 5. Generate
./generate.sh "A red fox walks through fresh snow in a pine forest. \
Medium tracking shot, natural winter light, realistic fur, \
soft footsteps in snow and gentle wind in the trees." \
  608 352 22 4 first-run.mp4 42
```

`generate.sh` pins execution to the eGPU by name and **refuses to run** if Metal only
offers an integrated GPU — a silent fallback to an Intel UHD 630 would look like a
hang. Set `H3_GPU_NAME` if your card isn't a 6900.

## Usage

```
./generate.sh "PROMPT" [WIDTH] [HEIGHT] [FRAMES] [STEPS] [OUTPUT] [SEED]
```

- Width and height must be multiples of 32.
- **Frame counts snap to 5 + 17k**: 22, 39, 56, 73, 90, 107, 124 … up to 362
  (0.9 s – 15 s at 24 fps). All lengths work since the SDPA fix; before it,
  anything whose joint sequence crossed ~6193 tokens produced mush.
- Cost scales roughly linearly in frames at this resolution: ~4 min for 22 frames,
  ~14 min for 124.
- Output is h264 + AAC in `outputs/`.

**Verify, don't trust.** Every failure mode we hit produced a valid MP4 that passed
`ffprobe` with exit code 0. Two habits that caught everything:

```bash
# luma screen: healthy clips average YAVG ~106-120, corrupt ones 36-65
ffprobe -v error -f lavfi "movie=out.mp4,signalstats" \
  -show_entries frame_tags=lavfi.signalstats.YAVG -of csv=p=0 |
  awk '{s+=$1;n++} END {print s/n}'

# then look at actual pixels
ffmpeg -i out.mp4 -vf "select='not(mod(n\,18))',scale=304:176,tile=3x2" \
  -frames:v 1 grid.png && open grid.png
```

The reference invariant for the code itself: the setup prompt above at 608×352/22/4,
seed 42 must produce md5 `886b40d10c5a83fb01393a4c62bdfcbd`. Every performance commit
in `patches/` preserved it.

## Environment knobs

| variable | effect |
|---|---|
| `H3_METAL_DEVICE_NAME` / `_INDEX` / `_REGISTRY_ID` | select the GPU; refuses to fall back |
| `H3_PROFILE=1` | per-phase profile: wall, encode, wait, root-gpu, **mps-gpu**, dispatch counts |
| `H3_METAL_FLUSH_EVERY` / `H3_METAL_MAX_INFLIGHT` | command-buffer bounding (defaults 4 / 2 on discrete GPUs; prevents the macOS GPU watchdog kill) |
| `H3_METAL_NO_VRAM_WEIGHTS` / `_NO_VRAM_ACTIVATIONS` | disable the two big eGPU wins (for A/B only — 8-13× slower) |
| `H3_STREAM_PAGE_CACHE=1` | let repeat runs serve DiT reads from RAM |
| `H3_STREAM_MMAP=1` | mmap'd blit source — **measured 32% slower**, kept so nobody retries it |
| `H3_DEBUG_STREAM_SPLIT=1` | per-batch upload wait telemetry |

On profiling: `root-gpu` counts only root command-buffer timestamps and **understates
GPU time ~10×** when MPSGraph is involved (it commits child buffers via
`commitAndContinue`). Patch 0011 adds `mps-gpu`, which captures the retired roots;
`gpu-total = root-gpu + mps-gpu` is the honest number. This mis-read once retired a
whole optimization plan — see `logs/42-reconciliation.md`.

## Why an eGPU port at all

Upstream h3.c is written for Apple Silicon unified memory: every buffer lives in
`MTLResourceStorageModeShared`. Over Thunderbolt that means the GPU reads host RAM at
~1.7 GB/s instead of VRAM at ~478 GB/s — a 270× gap that made single dispatches take
23 s and trip the macOS GPU watchdog. The port (patches 0001–0010):

- explicit device selection, refusing silent fallback (0001, 0002)
- streamed DiT weights held **in VRAM**, bounded command buffers (0003) — the watchdog fix
- an autorelease pool per AdaLN block, freeing 24.2 GiB of host memory (0004)
- activations in device-local VRAM — **8.46× on the denoise** (0005)
- upload batching/overlap experiments, measured and kept honest, including one
  committed negative result (0006–0010)

Every change is gated on `hasUnifiedMemory`, so on Apple Silicon the fork behaves
byte-identically to upstream and stays upstreamable. The workload ends up
**bus-bound, not compute-bound**: host→VRAM DMA runs at 96% of what a 20 Gb/s
Thunderbolt link sustains, and the weight stream hides completely behind compute.
